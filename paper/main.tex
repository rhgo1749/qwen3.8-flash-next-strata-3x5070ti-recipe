\begin{abstract}
Partially offloaded mixture-of-experts (MoE) runtimes can keep tens of GiB of expert weights in page-locked host memory while caching a working set on each GPU. Running one inference process per GPU makes request progress independent---useful on consumer workstations where GPU performance and PCIe links differ---but a runtime that allocates a private pinned expert arena per process also replicates its dominant host-memory object. We evaluate a narrow state-ownership split: each complete request is assigned to one GPU lane; all lane processes map one physical shared expert arena; and CUDA state, GPU expert caches, KV state, speculative-decoding state, and sessions remain lane-local. The lane mode therefore has no mandatory token-by-token cross-GPU dependency by construction. We do not claim that it is universally faster than coupled model parallelism.

On Strata 0.1.27 with Qwen3.8-Flash-Next IQ3\_S, aggregate completion throughput across independent requests increases from \textbf{71.5 tok/s} on one RTX 5070 Ti to \textbf{137.6 tok/s} on two and \textbf{191.8 tok/s} on three, corresponding to point speedups of \textbf{1.93$\times$} and \textbf{2.68$\times$} and parallel efficiencies of \textbf{96.3\%} and \textbf{89.5\%}. Sharing the host expert arena reduces a two-engine PSS snapshot from \textbf{95.3 GiB} to \textbf{52.1 GiB}, a measured reduction of \textbf{43.2 GiB (45.4\%)}; the same 46.8-GiB \texttt{rw-s} mapping is physically shared by both processes. In an interleaved same-generation heterogeneous experiment, an RTX 5070 Ti averages 73.01 tok/s alone and 72.36 tok/s while an RTX 5060 Ti concurrently contributes 59.14 tok/s. The concurrent-minus-solo change is $-0.65$ tok/s ($-0.9\%$; Welch 95\% CI $[-2.71,+1.41]$ tok/s, $p=0.50$), so this experiment does not resolve effects smaller than about a few percent.

The measured operating point is therefore memory-feasible independent serving over shared pinned host state. The evidence supports strong three-lane scaling and physical host-memory sharing on one consumer workstation; broader heterogeneity and direct comparisons with coupled execution remain future work.
\end{abstract}

\section{Introduction}
Large sparse MoE models are attractive on consumer hardware because only a subset of experts is active for each token. Their total expert population can nevertheless exceed the VRAM of a 16~GB GPU. Offload runtimes therefore place some or most expert state in host memory and keep only a working set on the accelerator, turning inference into a hierarchy involving GPU VRAM, host DRAM, PCIe, CPU execution, and sometimes storage~\cite{flexgen,fiddler,ktransformers,moelightning}.

Multiple consumer GPUs create a second constraint: the devices and links are not necessarily symmetric. Coupled multi-GPU strategies may place multiple devices on one request's progress path, and prior heterogeneous-serving systems explicitly model unequal GPU and network capacities~\cite{hexgen,helix,melange}. DWDP likewise identifies layer-wise synchronization and load imbalance as a source of sensitivity in distributed MoE inference~\cite{dwdp}. This paper does \emph{not} measure a coupled baseline on the reference workstation, so we use these systems only as motivation rather than as a performance comparison.

Request-level replication takes the opposite operating point: run one ordinary inference engine per GPU and route different requests to different engines. In that mode a lane has no algorithmic requirement to wait for another lane at each token step. The cost is memory. In Strata, the partially offloaded MoE engine allocates a large pinned anonymous host expert arena for DMA. Naively launching several processes therefore duplicates that allocation even though its expert contents are logically identical after initialization.

We apply one design principle: \emph{couple lanes through shared model backing, but keep progress-bearing execution state lane-local}. Concretely:
\begin{enumerate}
    \item \textbf{Independent request lanes} assign one complete request to one GPU engine, avoiding mandatory token-step dependencies between lanes.
    \item \textbf{A shared pinned host expert arena} lets those engine processes reuse one physical expert backing while retaining private CUDA, cache, KV, speculation, and session state.
\end{enumerate}

The design is intentionally narrow. It targets concurrent serving, not single-request acceleration, and it requires each participating GPU to fit one complete lane's device-resident working state. We do not claim to invent data parallelism, shared memory mapping, or weight sharing. The contribution is an implementation and measurement study of this ownership boundary for partially offloaded autoregressive MoE inference on a consumer workstation.

\paragraph{Contributions.}
This work makes four measured contributions:
\begin{itemize}
    \item We make Strata's pinned host expert arena cross-process shared without changing the numerical MoE kernels or the ordinary single-GPU allocation path when shared mode is disabled.
    \item We measure 1$\rightarrow$2$\rightarrow$3 independent-lane scaling on an x8/x8/x4 consumer PCIe topology, reaching a point estimate of 89.5\% three-lane parallel efficiency.
    \item We provide direct OS-level evidence of physical arena sharing and measure a 43.2~GiB (45.4\%) two-engine PSS reduction.
    \item We quantify one same-generation heterogeneous pair with confidence intervals and characterize workload sensitivity, while explicitly separating these observations from broader heterogeneity or causal claims.
\end{itemize}

\section{Motivation and Design}
\subsection{Keeping lane progress off a shared token-step path}
For a multi-GPU strategy that introduces a repeated barrier or dependency across $N$ devices, if device $i$ contributes step time $t_i$, a simplified lower-bound structure is
\begin{equation}
T_{\mathrm{step}}^{\mathrm{sync}} \gtrsim \max_i t_i + T_{\mathrm{coord}},
\label{eq:sync}
\end{equation}
where $T_{\mathrm{coord}}$ captures communication and synchronization overhead. This is a motivation model rather than a measured baseline for our workstation: tensor, pipeline, layer, and expert parallelism differ substantially, and heterogeneity-aware partitioning can mitigate imbalance~\cite{hexgen,helix}.

Independent request lanes change the ownership and objective. Let $r_i$ be the sustained request-generation rate of lane $i$. Aggregate serving capacity can be written conceptually as
\begin{equation}
R_{\mathrm{lanes}} \approx \sum_i r_i - \Delta_{\mathrm{shared}},
\label{eq:aggregate}
\end{equation}
where $\Delta_{\mathrm{shared}}$ represents contention for host memory bandwidth, CPU resources, and PCIe/root-complex resources. A slower device contributes less capacity, but lane progress is not joined by a mandatory token-step barrier. This does not imply zero interference: the shared-resource term is precisely what our measurements probe.

\subsection{The replica-memory problem}
If every lane privately allocates a host expert arena of size $M_E$, then with $N$ replicas the host requirement is approximately
\begin{equation}
M_{\mathrm{private}} \approx N M_E + \sum_{i=1}^{N} M_{\mathrm{lane},i},
\label{eq:private}
\end{equation}
where $M_{\mathrm{lane},i}$ covers private session, KV, runtime, and bookkeeping state. With one shared expert arena,
\begin{equation}
M_{\mathrm{shared}} \approx M_E + \sum_{i=1}^{N} M_{\mathrm{lane},i}.
\label{eq:shared}
\end{equation}
The savings approach $(N-1)M_E$ as the shared object dominates process-private state.

\subsection{State ownership}
The design shares only the large model state that is naturally identical across replicas. The shared category is the host expert backing. Lane-local state includes CUDA contexts and streams, GPU hot-expert caches, adaptive-residency metadata, GPU-resident KV, host-KV/session state, speculative/MTP state, request state, and cancellation. This boundary avoids turning normal serving progress into a distributed consistency problem. The current file-backed mapping remains writable at the OS level after initialization, so memory corruption of the shared arena is a shared failure mode; this prototype does not claim fault isolation of the weight backing.

\section{Implementation}
We implement the architecture as an opt-in compatibility layer around Strata~\cite{strata}. Each GPU lane is an ordinary Strata engine process. A supervisor sanitizes generated lane configurations so inherited \texttt{gpu} and \texttt{layer\_split} settings cannot accidentally expand one lane back into coupled multi-GPU execution.

On Linux, the fork intercepts only the exact pinned-arena allocation when the shared-arena path and byte count are explicitly supplied. Otherwise, the upstream anonymous/hugetlb allocation path remains unchanged. For the evaluated 0.1.27 baseline, the retained upstream pinned implementation is byte-identical to upstream Strata 0.1.27; the fork changes the allocation ownership boundary rather than the numerical MoE kernels. The shared mapping is \texttt{rw-s}: expert contents are logically read-mostly after population, but read-only protection is not yet enforced with \texttt{mprotect}.

The paper-validation fork commit is \texttt{6cf101d}; upstream Strata 0.1.27 is \texttt{a790805}. The evaluated binary is \texttt{build-production-027/strata}; its full commit IDs and SHA-256 are pinned in the companion artifact. The companion artifact retains repetition-level CSVs and methodology documents~\cite{artifact}.

\paragraph{Scaling protocol.}
For 1, 2, and 3 active lanes, a fixed warm prompt produces 512 completion tokens per lane. The primary scaling metric is \emph{common-wall aggregate completion throughput}: total completion tokens across all active requests divided by one client wall interval measured around the concurrent HTTP requests. It is a makespan-based metric and therefore intentionally penalizes the slowest completion; it should not be confused with the engine's lane-local decode-TG metric used below. Five completed repetitions are retained at each point. No completed scaling observation was removed.

\paragraph{Memory protocol.}
The private-vs-shared ablation uses two x8 RTX 5070 Ti engines with reduced 32,768-token context and 8,192 resident-KV tokens so the private control is feasible. It is a structural paired snapshot rather than a repeated statistical benchmark. Physical memory is measured from \texttt{/proc/<pid>/smaps\_rollup} and the arena mapping itself, emphasizing PSS and shared/private dirty accounting rather than RSS alone.

\paragraph{Heterogeneous protocol.}
The RTX 5070 Ti x8 solo condition and the RTX 5070 Ti x8 + RTX 5060 Ti x4 concurrent condition follow an \texttt{ABBAABBAABBAABBA} order to reduce time-order bias. The heterogeneity metric is the engine-reported lane-local decode rate, not common-wall aggregate throughput. Eight completed fast-lane repetitions are retained per condition, with the slow lane measured concurrently. The retained dataset does not include a full-length RTX 5060 Ti solo control.

\paragraph{Workloads.}
Five repetitions are retained for fiction, coding, reasoning, and long-review workload/bucket states. No-reuse PP and warm steady-state TG are treated as separate measurement classes. A mixed-serving experiment rotates fiction, coding, and reasoning across the x8/x8/x4 5070 Ti lanes for nine common-wall runs.

\paragraph{Data hygiene.}
The heterogeneous raw JSONL contains one malformed trailing fragment written after the last valid summary record. All 8 solo and 8 concurrent completed measurements are valid and retained; only that unparsable non-observation is absent from the publication CSV. The scaling dataset retains all completed runs, including the slowest three-lane repetition.

\section{Evaluation}
\subsection{RQ1: How does independent-request capacity scale to three lanes?}
Figure~\ref{fig:scaling} shows strong but sublinear scaling in common-wall aggregate completion throughput. The mean increases from 71.45 tok/s on one x8 5070 Ti to 137.57 tok/s on two x8 cards and 191.75 tok/s after adding the x4 5070 Ti. These correspond to point speedups of 1.93$\times$ and 2.68$\times$, or 96.3\% and 89.5\% parallel efficiency relative to the one-x8-lane mean. Approximate t-based 95\% CIs for the throughput means are 70.06--72.84, 134.85--140.29, and 182.76--200.74 tok/s; the three-lane range is 182.63--199.20 tok/s.

PCIe width, CPU/core placement, DRAM traffic, thermal state, and other shared resources are confounded. We therefore treat 89.5\% as an operating-point measurement rather than evidence for a particular contention mechanism.

\subsection{RQ2: Does shared backing eliminate replica RAM duplication?}
The two-engine private control measures 95.3~GiB PSS, while shared backing measures 52.1~GiB, a reduction of 43.2~GiB or 45.4\% (Figure~\ref{fig:memory}). The shared arena appears as the same \texttt{rw-s} \texttt{/dev/shm} mapping in both engines. The 49,116,200~KiB arena mapping is accounted as \texttt{Shared\_Dirty}, with \texttt{Private\_Dirty=0}. This is direct OS-level evidence of physical sharing rather than an inference from virtual address size or RSS.

\subsection{RQ3: How much interference is visible in one heterogeneous pair?}
The RTX 5070 Ti averages 73.01$\pm$1.41 tok/s alone and 72.36$\pm$2.26 tok/s while an RTX 5060 Ti x4 simultaneously serves at 59.14$\pm$1.24 tok/s (Figure~\ref{fig:hetero}). Using the eight run means per arm, the concurrent-minus-solo change is $-0.65$ tok/s ($-0.9\%$). A Welch comparison gives $t=-0.69$, $p=0.50$, with a 95\% CI of $[-2.71,+1.41]$ tok/s (approximately $-3.7\%$ to $+1.9\%$ relative to the solo mean). Thus this experiment finds no statistically resolved mean slowdown, but it cannot exclude effects of a few percent; the concurrent SD also rises from 1.41 to 2.26 tok/s.

\subsection{Mixed-content three-lane rotation}
To move beyond identical prompts, fiction, coding, and reasoning are rotated across GPU0 x8 / GPU2 x8 / GPU1 x4. Nine common-wall runs produce 187.15$\pm$5.63 tok/s aggregate, range 176.85--196.18 tok/s. We treat this as a mixed-content support experiment rather than a trace-driven serving benchmark; it shows that the three-lane operating point persists when the lanes do not all decode the same prompt.

\section{Related Work}
\paragraph{Heterogeneous GPU serving.}
HexGen partitions tensor and pipeline parallel inference asymmetrically across heterogeneous GPUs and networks~\cite{hexgen}; Helix jointly optimizes model placement and request scheduling over heterogeneous GPU clusters~\cite{helix}; and M\'elange chooses heterogeneous GPU mixes for cost-efficient serving under workload and SLO constraints~\cite{melange}. These systems make clear that heterogeneity is not a new problem. Our setting is narrower: one consumer workstation, independent request replicas, and a model whose expert population already resides largely in host memory. We do not compare end-to-end throughput against these cluster-scale schedulers.

\paragraph{CPU/GPU and storage offload for MoE inference.}
FlexGen studies coordinated GPU/CPU/storage offload for large models~\cite{flexgen}. Fiddler reduces MoE data movement by orchestrating CPU and GPU computation~\cite{fiddler}; KTransformers develops high-performance CPU/GPU hybrid MoE inference with asynchronous scheduling~\cite{ktransformers}; and MoE-Lightning pipelines CPU, GPU, and I/O resources for high-throughput MoE inference on memory-constrained GPUs~\cite{moelightning}. This body of work establishes host-resident experts and heterogeneous CPU/GPU execution as prior art. Our paper addresses a different ownership question: when several offloaded engine processes coexist, can their dominant pinned host expert backing be physically shared while request progress remains process-local?

\paragraph{Distributed or shared model weights.}
DeepSpeed-MoE established optimized distributed MoE inference~\cite{deepspeedmoe}. DWDP preserves independent data-parallel progress while distributing MoE weights across peer GPUs and fetching missing experts on demand~\cite{dwdp}. SiDP similarly treats weights as a bandwidth-backed shared resource, using remote-weight streaming or remote computation on datacenter GPUs~\cite{sidp}. vLLM-Omni Distributed Layerwise Offload uses mmap-backed checkpoint views to share OS page-cache pages across processes and can optionally reconstruct sharded layers with AllGather for diffusion workloads~\cite{vllmomni}. These are important precedents: neither data-parallel independence nor mmap/page-cache sharing is novel here. Our measured mechanism is specifically a cross-process shared backing for the pinned host expert arena of an autoregressive offload runtime, while each lane retains its own GPU hot cache, KV, speculation, and request state.

\paragraph{Serving memory management and consumer runtimes.}
vLLM's PagedAttention reduces KV-cache fragmentation and supports sharing at the request-memory level~\cite{vllm}. FreeToken explores MoE offloading and host-residency tradeoffs on consumer/workstation hardware~\cite{freetoken}. Our contribution is complementary and deliberately smaller: a replica-memory optimization and serving topology for one partially offloaded MoE runtime, not a general replacement for these engines.
\section{Discussion}
\subsection{Why the two mechanisms belong together}
Request-level replicas remove mandatory token-step dependencies between replicas, but a pinned-anonymous offload runtime can pay for that independence by duplicating its largest host allocation. Shared backing reduces that memory cost, but it is operationally simple only when progress-bearing execution state remains private. The design principle is therefore: \emph{share model backing, not request progress}. The paper's measurements quantify the resulting operating point; they do not establish that independent lanes dominate heterogeneity-aware model parallelism.

\subsection{When this design is the wrong choice}
The architecture does not make one request faster with additional GPUs. A request that cannot fit one lane, or an application dominated by single-request latency, may prefer tensor, pipeline, layer, or expert parallelism. Every participating GPU must independently fit one lane's device-resident working set (hot experts, KV, and runtime state), so very small-VRAM cards may be unusable even when a coupled scheme could pool capacity. Independent lanes also duplicate the GPU-resident hot cache across replicas; this paper removes host-arena duplication, not all model-state duplication. If all weights fit comfortably in every GPU and host RAM is not constraining, the shared arena offers less value.

\subsection{Scaling ceiling}
Equation~\ref{eq:aggregate} includes a shared-contention term for a reason. CPU execution, DRAM bandwidth, PCIe root-complex bandwidth, and shared filesystem/page-cache behavior remain finite. Three lanes at 89.5\% efficiency show that the reference host has useful remaining concurrency, not that scaling will remain linear indefinitely. A larger-GPU-count study is future work.

\section{Limitations}
The evidence is a measurement study on one workstation, one model family, one runtime, and at most three primary serving lanes. We do not include a same-host coupled layer/tensor/expert-parallel baseline or a one-GPU multi-request batching baseline; consequently the paper claims an operating point, not superiority over those alternatives. The heterogeneous experiment covers only one same-generation 5070 Ti + 5060 Ti pair, lacks a retained full-length 5060 Ti solo arm, and confounds GPU model with x8/x4 link width.

The PSS ablation is a single paired structural snapshot at reduced 32K context / 8K resident KV rather than the 262K / 32K serving configuration, and system-wide memory counters were not retained. The 43.2~GiB PSS reduction should therefore not be interpreted as an exact copy of the 46.8~GiB mapped arena. CPU CCD/core-placement effects, DRAM bandwidth, PCIe-root contention, and thermal/power behavior are not independently decomposed. The benchmark-start clock/undervolt state was not snapshotted.

The current Linux backing remains \texttt{rw-s}; read-only protection is not enforced after population, so shared-memory corruption is a cross-lane failure mode. We therefore make no fault-isolation claim for the weight arena. Finally, the workload study is observational: speculative acceptance, routing locality, and context length are not independently controlled, and no adaptive swaps occur in the retained workload windows.

\section{Reproducibility and Artifact}
The companion repository keeps the runtime implementation and machine-specific evidence deliberately separate. The Strata fork holds generic serving code and contracts, while the recipe repository holds reference-host methodology, raw repetition-level CSVs, current and historical promotion records, and reporting rules~\cite{artifact}. The final evidence pin records exact fork/upstream commits, binary SHA-256, driver/CUDA versions, topology, prompt hashes, and anomaly notes. Historical 0.1.22/0.1.24 measurements remain available but are not treated as strict software-version A/Bs when prompts or measurement contracts differ.

The central 0.1.27 artifact consists of 68 retained systems observations, 70 workload repetitions, and a separate validation/provenance CSV. The public repository exposes the current evidence and the paper branch; headline values can be recomputed from the retained CSVs. One malformed trailing JSON fragment in the heterogeneous raw log is documented and is not a completed measurement.

\section{Conclusion}
We evaluate a simple ownership boundary for partially offloaded MoE serving: complete requests progress in independent GPU processes, while the dominant pinned host expert arena is physically shared. The implementation changes host-allocation ownership rather than the numerical MoE kernels.

On one consumer workstation, common-wall aggregate completion throughput across independent requests reaches 191.75 tok/s on three RTX 5070 Ti lanes, a 2.68$\times$ point speedup over one lane at 89.5\% parallel efficiency. A two-engine structural ablation measures a 43.2~GiB (45.4\%) PSS reduction with direct OS evidence that the 46.8-GiB arena mapping is physically shared. In one same-generation heterogeneous pair, the 5070 Ti mean changes by $-0.65$ tok/s while a 5060 Ti serves concurrently; the 95\% CI still permits a few-percent effect, so broader heterogeneity claims require more data.

The result is best understood as a memory-feasible independent-serving operating point, not as a universal replacement for model parallelism. Coupled execution remains appropriate when one request needs pooled GPU capacity; independent lanes are attractive when concurrent requests exist and one wants shared host model state without a mandatory token-step dependency between replicas.
